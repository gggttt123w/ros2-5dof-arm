## 3. 接口契约

这一节是全文最重要的部分——**串联的本质就是让三层遵守同一份契约**。

### 3.1 舵机串口协议（USART2 @ 115200）

代码位置：`Core/Src/robot_arm.c`

| 命令 | 方向 | 含义 |
|---|---|---|
| `#000P1500T1000!` | → | 舵机 0 转到位置 1500，用时 1000ms |
| `#000PRAD!` | → / ← | 读角度，回包里取 `P` 后面的数字 |
| `#000PMOD!` | → / ← | 读模式，回包里取 `D` 后面的数字 |
| `#000PRTE!` | → / ← | 读温度，回包里取 `T` 后面的数字 |
| `#000PRTV!` | → / ← | 读电压，回包里取 `V` 后面的数字 |

初始化时（`robot_arm_init`）一次性给 6 个舵机发：

```
{#000P1500T1000!#001P1500T1000!#002P1500T1000!#003P1500T1000!#004P1500T1000!#005P1500T1000!}
```

即**全部回到中位 1500**。这同时也是你的「机械零位」，和 URDF 里全零姿态是同一件事——**这个对应关系必须保证，否则 RViz 和实机会对不上**。

> ⚠️ 总线舵机通常是**单线半双工** TTL。代码里用的是 USART2 的 TX/RX 两线，
> 实际板子上大概率有收发切换电路或者 TX/RX 短接。**接线方式需要你确认**（推断）。

### 3.2 CAN 协议（STM32 ↔ KickPi）@ 250 kbps

**下行：KickPi → STM32，ID `0x104`**（`CAN_ID_CMD_DOWN`）

| 字节 | 含义 |
|---|---|
| 0 | 舵机 id，0~5 |
| 1 | 命令码：`1`=ASKFORSETPOS　`2`=ASKFORSTATUS　`3`=ASKFORALL |
| 2-3 | `target_pos`，**小端** uint16 |
| 4-5 | `time`（ms），**小端** uint16 |
| 6-7 | 未使用 |

**上行：STM32 → KickPi，ID `0x200`**（`GETANGLE`）

| 字节 | 含义 |
|---|---|
| 0 | 舵机 id |
| 1-2 | `cur_pos`，**小端** uint16 |
| 3 | 温度（℃） |
| 4 | 电压 × 10 |
| 5-7 | 补零 |

**三个命令码的行为差异**（`Core/Src/freertos.c` 的 `UART_task`）：

| 命令码 | 做什么 | 有 CAN 回复吗 |
|---|---|---|
| `ASKFORSETPOS` (1) | 只发位置指令 | **没有** |
| `ASKFORSTATUS` (2) | 只读温度/电压/角度 | 有 |
| `ASKFORALL` (3) | 先发位置，再读状态 | 有 |

> `GETTANDV 0x201` 和 `GETERR 0x202` 在 `robot_arm.h` 里定义了，
> 但**代码从没往这两个 ID 发过任何东西**——是预留的。

**波特率对得上吗？** 对得上，我算过：

```
STM32: SYSCLK 168MHz → APB1 = 168/4 = 42MHz
       Prescaler=12 → tq = 12/42MHz = 285.7ns
       Bit time = 1 + BS1(11) + BS2(2) = 14 tq = 4.0µs  →  250 kbit/s ✅
       采样点 = 12/14 = 85.7%（正常值）

KickPi: can_init.h 里 bitrate 250000  ✅
```

两边一致。**但两个 120Ω 终端电阻必须有**，否则通信不稳或直接不通。

### 3.3 ROS 2 侧接口（还不存在，需要设计）

这块是空白，得先定契约。建议：

| 项 | 建议 |
|---|---|
| 关节名 ↔ 舵机 id | `joint1`→0, `joint2`→1, `joint3`→2, `joint4`→3, `joint5`→4, 夹爪→5 |
| 角度单位 | ROS 用 **弧度**，舵机用 **0~2500 的位置值**，必须换算 |
| 上行话题 | `/joint_states`（`sensor_msgs/JointState`） |
| 下行话题 | `/joint_commands` 或 `trajectory_msgs/JointTrajectory` |
| 状态话题 | `/servo_status`（温度/电压，用于过热保护） |

**换算关系是最大的未定项。** URDF 里 joint1 限位 ±90°，而舵机位置范围是多少（0~2500？500~2500？），
以及「舵机值 1500 ↔ URDF 零位」是否线性对应，**都需要实测标定**。代码里
`N_MAX 2500` / `T_NORMAL 1000` 定义了但从未使用，说明这块还没做。

## 4. 一次完整的数据流

以「让 3 号舵机（joint4）转到 2000，用时 500ms」为例：

```
① ROS 2 节点
   发布 /joint_commands: joint4 = <角度>
   换算成舵机位置 2000、时间 500

② 通过以太网送到 KickPi                     ← ❌ 这一段不存在
   
③ CanServer
   Can_Write(data, 0x104, 6)
   data = [03, 01, D0, 07, F4, 01]
          id  ask  └2000┘  └─500─┘  (小端)

④ CAN 总线 → STM32

⑤ HAL_CAN_RxFifo0MsgPendingCallback (中断)
   存进 16 帧环形缓冲

⑥ CAN_Rx_task (osPriorityRealtime3)
   轮询 CAN_GetRxFrame() → 看到 id==0x104
   校验 len>=6、id<=SEVRO_NUMBER
   解析成 CmdMsg_t{id=3, ask=1, target_pos=2000, time=500}
   塞进 CMD_Queue (容量 16)

⑦ UART_task (osPriorityRealtime1)
   阻塞在 CMD_Queue 上，取到后 switch(ask)
   case ASKFORSETPOS → Servo_position_set(3, 2000, 500)

⑧ USART2 @115200 发出文本
   "#003P2000T0500!"

⑨ 3 号舵机转动 500ms 到位

── 如果要状态回传（ask=2 或 3），后面还有一半 ──

⑩ UART_task 调 Servo_temp_and_v_get() + Servo_position_get()
   读 USART2 的回包

⑪ 装满 ServoMsg_t，塞进 Status_Queue

⑫ CAN_Tx_task (osPriorityHigh7)
   阻塞在 Status_Queue 上，取到后
   CAN_Servo_status_send_pkg() 打包成 8 字节
   CAN_Send(0x200, pkg, 8)

⑬ CAN → KickPi，CanServer 收 0x200

⑭ 再通过以太网回 ROS 2，填进 /joint_states      ← ❌ 这一段不存在
```

**注意 ⑫ 的一个细节**：`CAN_Tx_task` 把 `0x200` 作为**所有**状态回复的 ID，
不带舵机号区分（舵机号在 `pkg[0]` 里）。这意味着上位机得靠数据内容分辨是谁的状态。

## 5. 步骤教程

建议**自下而上**，一层验证通过再往上。每层都能独立验证，不要一次全接。

### 阶段 A：STM32 ↔ 舵机　✅ 已验证通过

> **状态：你已实测跑通。** 本阶段保留作为「怎么复现 / 出问题时怎么排查」的参考，
> 如果你要重新烧固件或者换舵机，按下面走。

**目标**：确认 6 个舵机能被 STM32 通过串口控制。

**A1. 硬件**
- STM32 USART2 ↔ 舵机总线（注意半双工问题，见 §3.1）
- 舵机单独供电，**别从 STM32 的 3.3V 取电**——总线舵机堵转电流能到安培级
- 共地

**A2. 单独验证串口（推荐，先绕开 STM32）**
用 USB-TTL 直接把舵机接到 PC，115200 发：

```
#000PRAD!
```

能收到 `#000P1500!` 之类就说明舵机和线是好的。这一步能省掉大量排查时间。

**A3. 烧录 STM32 固件**

工程用的是 CMake + Ninja + `arm-none-eabi` 工具链（`cmake/gcc-arm-none-eabi.cmake`），
所以本机得先有 `arm-none-eabi-gcc` 和 `ninja`。

```bash
cd stm32_firmware
cmake --preset Debug              # 输出到 build/Debug（.clangd 也指向这里）
cmake --build --preset Debug      # 等价于 cmake --build build/Debug

# 烧录：openocd.cfg 已配好 interface/stlink.cfg + target/stm32f4x.cfg
openocd -f openocd.cfg -c "program build/Debug/robot_arm.elf verify reset exit"
```

> `openocd.cfg` 里是 `reset_config none`，如果你的下载器不支持 `reset`，
> 把命令末尾的 `reset` 去掉试试。

**A4. 验证**
- USART3（调试串口）115200 应该打印 `Init OK`
- 6 个舵机应该一起转到 1500 中位

> 注意 `robot_arm.h` 里 `DEBUG_MODE 1`，读状态时会把回包往 USART3 大量打印。
> 调试完记得关掉，否则会和上位机抢串口。

**A5. 如果不动**
- 检查舵机 id 是否真的是 0~5（出厂可能是别的）
- 检查波特率（115200）
- 检查 TX/RX 是否接反

### 阶段 B：KickPi ↔ STM32（CAN）　✅ 已验证通过

> **状态：你已实测跑通。** 下面是复现步骤和排查手册。
> 这一阶段的成果是「证明了链路可用」，但用的是 `cansend` / `candump` 手工发的，
> **没有留下任何程序**——这正是阶段 C 要补的。

**目标**：用 `candump` / `cansend` 手工和 STM32 对话。

**B1. 装工具**
```bash
ssh kickpi@10.249.86.224
sudo apt install can-utils
```

**B2. 起 can0**（波特率必须和 STM32 一致）
```bash
sudo ip link set can0 type can bitrate 250000 triple-sampling on
sudo ip link set can0 up
ip -details link show can0        # 确认 state UP，波特率对
```

**B3. 先看 STM32 有没有在发东西**
```bash
candump can0
```
STM32 只在被查询后才回复，所以**这里应该是安静的**——如果一直有帧，说明有别的设备或者有问题。

**B4. 发一条命令试试**

`cansend` 的格式是 `<id>#<hexdata>`。发「3 号舵机转到 2000，500ms」：

```bash
cansend can0 104#0301D007F401
```

拆解：
| 段 | 值 | 含义 |
|---|---|---|
| `104` | 0x104 | CAN ID |
| `03` | 3 | 舵机 id |
| `01` | 1 | ASKFORSETPOS |
| `D0 07` | 2000 小端 | target_pos |
| `F4 01` | 500 小端 | time |

**B5. 发一条要回复的**
```bash
cansend can0 104#030200000000      # id=3, ask=2 (ASKFORSTATUS)
candump can0                       # 应该收到 0x200
```

预期收到 `0x200`，`pkg[0]=0x03`，`pkg[1..2]` 是当前位置。

> **没有接舵机也能测通 CAN**：`ASKFORSTATUS` 会因为串口超时（1000ms）而返回垃圾数据，
> 但**帧本身会正常回来**。这就足够证明 CAN 链路是通的。这是很划算的一步。

**B6. 常见坑**
- `can0` 起不来 → 内核驱动问题，他们仓库里那个 `patches/rockchip_canfd-fix-rx-stats.patch` 就是为这个准备的
- 发得出去收不到 → 十有八九是**终端电阻**，或者两端波特率不一致
- 报错帧暴增 → 用 `candump -e can0` 看错误帧

### 阶段 C：KickPi ↔ ROS 2（要写代码）

**目标**：ROS 2 里的角度能变成 CAN 帧，CAN 回来的状态能变成 `/joint_states`。

这一段**没有现成代码**，按依赖顺序分三步：

`include/can_init.h` 只有三个宏，外面根本用不了。需要：

**C2. 写 CanServer 的 main：一个 CAN ↔ 网络 的转发程序**

两种做法：

| 方案 | 说明 | 适合 |
|---|---|---|
| **A. CanServer 直接做 ROS 2 节点** | 在 KickPi 上编 ROS 2，用 `rclcpp` 收发 | 板子上装了 ROS 2 才行（现在没装） |
| **B. CanServer 是普通 TCP/UDP 服务** | ROS 2 侧再写个节点连它 | 板子不用装 ROS 2，耦合低 |

考虑到板子现在**没有 ROS 2**、且内存只有 3.8G，**方案 B 更省事**。但如果你以后想在板子上跑
导航/规划，方案 A 更顺。

**C3. 写 ROS 2 节点**

至少要做的换算：
```
URDF 角度(rad) ←→ 舵机位置(0~2500)
```
外加：零位对齐、各关节方向（正负号）、限位映射、以及 `time` 参数的确定。

**C4. 接进 RViz 验证**

这个已经有基础了——`display.launch.py` 只要把 `/joint_states` 的来源从
`joint_state_publisher_gui`（假数据）换成真实驱动（真数据）就行。把 launch 里那个
GUI 节点去掉即可。

## 7. 读代码时发现的可疑点

> **重要前提：你已经实测跑通了，所以下面这些都不是「拦路虎」。**
>
> 能在实机上跑通，说明这些要么是**边界情况**（不触发就没事），
> 要么我对舵机回包格式的理解有偏差（我只是从代码反推的，没看过真实回包）。
> 按严重程度排，但请把「能不能跑通」当作比我的阅读更权威的证据。
>
> 其中 **a) 和 b) 两条现在就可以验证**：跑一次状态查询，看回传的
> 温度字节和电压字节对 6 个舵机是否都合理。如果都正常，那就是我想错了。

**以下全是我的阅读结论，我没有改任何一行代码**（你说了不要动）。

### 🔴 会出错的

**a) `Core/Src/robot_arm.c:70-98` — `Servo_temp_and_v_get` 名不副实**

函数名叫「读温度和电压」，参数也是 `double _temp_v[2]`，但**每个舵机只发一条查询**：

```c
if(id != 0)      len = snprintf(cmd, ..., "#%03dPRTE!", id);   // 只查温度
else if(id == 0) len = snprintf(cmd, ..., "#%03dPRTV!", id);   // 只查电压
```

也就是说：**id 0 能拿到电压但拿不到温度，其余 5 个能拿到温度但拿不到电压**，
另一项是缓冲区里的残留值。而上层 `CAN_Tx_task` 不加分辨地把两项都打包发出去了。

**b) `Core/Src/robot_arm.c:121-124` — 温度换算分支可疑**

```c
if((((uint16_t)T % 100) > 50) && st->id != 0){
    T = T - ((uint16_t)T % 100) + 100;
    T /= 100;
}
```

同一个字节，**温度低于某个阈值时原样输出，高于时除以 100**，单位不统一。
比如 T=50 时输出 50，T=60 时输出 1。看着像想处理某种特殊的回包格式，但逻辑不成立。
**建议实测一下舵机 `PRTE` 到底回什么**再定。

### 🟡 会吃亏的

**c) `Core/Src/robot_arm.c:111` — 命令缓冲区刚好卡死**

```c
#define Servo_CMD_LEN 16
snprintf(cmd, sizeof(cmd), "#%03dP%04dT%04d!", id, n, t);
```

`#000P1500T1000!` 正好 15 字符 + `\0` = 16，**一个字节余量都没有**。
一旦 `n` 或 `t` 超过 4 位（比如 `n=65535`），`snprintf` 会**静默截断**，发出一个残缺命令。
而 `Servo_position_set` 没有做范围检查，`N_MAX 2500` 定义了却从没用过。

**d) `Core/Src/freertos.c:267` — CAN 发送失败被忽略**

```c
CAN_Send(GETANGLE, (uint8_t*)pkg, 8);
```

`CAN_Send` 在三个发送邮箱都满时返回 `HAL_ERROR`，这里没接返回值，**状态帧会静默丢失**。

**e) `Core/Src/freertos.c:258, 285` — malloc 没检查返回值**

```c
ServoMsg_t *st = malloc(sizeof(ServoMsg_t));
```

两个任务各 malloc 一次，无 NULL 检查。实际影响很小（只执行一次、从不 free），
但 RTOS 里用堆要留意碎片。改成静态变量更稳。

### ★ 优先级次序会让串口空转饿死 CAN 发送

**这条单独拎出来说，因为它是架构层面的，不是某一行的笔误。**

三个任务的实际优先级（CMSIS-RTOS2 数值越大越高）：

```
CAN_Rx_task  Realtime3 = 51
UART_task    Realtime1 = 49      ← 比 High7 高！
CAN_Tx_task  High7     = 47
```

而 `robot_arm.c` 里所有串口调用都是**阻塞轮询版**（`HAL_UART_Receive`，
超时 1000ms，工程没配 DMA），空转时是真占 CPU。

**后果**：某个舵机掉线/没接时，`UART_task` 会在 `HAL_UART_Receive` 里空转最多 1 秒。
这 1 秒内它优先级高于 `CAN_Tx_task`，**状态回包全部被压住**。
如果 6 个舵机都掉线，一次轮询就是 6 秒。

CAN **接收**不受影响（`Realtime3` 最高，随时抢占），所以下行指令不会丢——
问题只出在上行状态回传的延迟上。

**两种改法**：

| 改法 | 改动量 | 效果 |
|---|---|---|
| `CAN_Tx_task` 提到 `osPriorityRealtime2`(50) | 改 1 行 | 让它低于 CAN 接收、高于串口，最快 |
| USART2 改 DMA + 中断，`UART_task` 阻塞在信号量 | 中等 | 根治，空转消失，CPU 让给其他任务 |

### 🔵 只是别扭

**f) `Core/Src/freertos.c:270, 321` — 不可达的 `osDelay(1)`**

前面 `osMessageQueueGet(..., portMAX_DELAY)` 是永久阻塞，`continue` 之后才轮到 `osDelay`，
所以那句 `osDelay(1)` 永远不会执行。

**g) `robot_arm.h:7` — 宏名有歧义**

```c
#define SEVRO_NUMBER 5
```

代码里到处用 `if(id > SEVRO_NUMBER)`，实际允许 id = 0~5，也就是 **6 个舵机**。
宏的名字读起来像「舵机数量 = 5」，容易误判。另外 `SEVRO` 是 `SERVO` 的拼写错误。
（数量是 6，和「5 自由度 + 1 夹爪」是对得上的 ✅）

**h) `MYWARE/aps6404/` — 整块是死代码**

`APS6404_Init()` 定义了，但**全工程没有任何地方调用它**。SPI3 初始化了，PSRAM 没用上。
8MB PSRAM 的用途（日志？轨迹缓冲？）还没落地。

**i) `Core/Src/can.c` — 没有 CAN 错误处理**

只开了硬件层的 `AutoBusOff`，没有 `HAL_CAN_ErrorCallback`，
总线关闭、错误计数、丢帧都不可见。`CAN_GetRxDropCount()` 这个接口写了但没人用。

## 8. 设计思路：为什么是这样

从代码反推出来的设计取舍，理解了这些，改动时才知道哪里能动、哪里不能动。

### 8.1 为什么舵机挂 UART 而不挂 CAN？

**因为舵机自己就带串口协议。** 这些总线舵机（`#000P1500T1000!` 这种）内部集成了
驱动板和位置反馈，出厂就是 TTL 串口，没法直接上 CAN。要上 CAN 就得在每个舵机前加转换器，
成本和复杂度都不划算。

### 8.2 那 CAN 是干嘛的？

**CAN 是 STM32 和 KickPi 之间的主干。** 选 CAN 而不是 UART/USB 的理由：

- **抗干扰**：机械臂上电机多，CAN 是差分信号，比单端 TTL 稳得多
- **距离**：几米内没问题，I2C/SPI 做不到
- **多主**：以后要加别的节点（力传感器、第二块板子）可以并联上去
- **自带 CRC 和重传**

**STM32 在这里的角色是「协议转换器」**——CAN 一侧对上位机，UART 一侧对舵机。
它不做运动学、不做规划，就是个搬运工。这个分工是对的：实时性要求高的放 MCU，
算力要求高的放上位机。

### 8.3 为什么要 FreeRTOS 分三个任务？

关键矛盾：**串口慢，CAN 不能等。**

USART2 是 115200，读一次舵机状态要发命令 + 等回包，`HAL_UART_Receive` 的超时是 **1000ms**。
而且注意——工程里用的是**阻塞轮询版**（`HAL_UART_Transmit` / `HAL_UART_Receive`，
不是 `_IT` 也不是 `_DMA`，`usart.c` 里根本没配串口 DMA）。
所以这一秒是**实打实占着 CPU 空转**，不是让出 CPU 去睡觉。

如果 CAN 收发和串口操作在同一个循环里，一次串口超时就会堵住 CAN 一秒钟。
所以拆成三个任务，用**两个消息队列**解耦（各 16 深度）：

```
CAN_Rx_task  (Realtime3 = 51)  ── 从环形缓冲取帧 → 校验 → 入 CMD_Queue
UART_task    (Realtime1 = 49)  ── 独占串口，收发的慢活都在它身上
CAN_Tx_task  (High7     = 47)  ── 从 Status_Queue 取 → 打包 → 发 CAN
```

**隔离效果是不对称的，这点很关键：**

| | 会被串口空转拖住吗 |
|---|---|
| CAN **接收** | ❌ 不会。`Realtime3`(51) 高于 `UART_task`(49)，随时能抢占 |
| CAN **发送** | ⚠️ **会**。`High7`(47) **低于** `UART_task`(49)，串口空转期间拿不到 CPU |

也就是说：某个舵机没接上或不应答时，`UART_task` 会在 `HAL_UART_Receive` 里空转最多 1 秒，
**这 1 秒内 `CAN_Tx_task` 被压住，状态回包会延迟最多 1 秒**。
接收侧不受影响，发送侧会卡。详见 §7 的 ★ 条。

### 8.4 为什么 CAN 收帧要用环形缓冲 + 中断？

CAN 帧可能**突发到达**（比如上位机连发 6 个舵机的状态查询）。
如果只在任务里轮询 HAL 的 FIFO，任务正忙时就会丢帧。

`can.c` 里的做法是：中断里把帧搬进 16 帧的环形缓冲，任务慢悠悠地取。
注释里还专门说明了为什么不需要关中断保护：

> head 只在 CAN 中断里写、tail 只在任务里写，两个都是 uint8_t
> —— Cortex-M4 上字节读写是原子的，且这是单生产者/单消费者结构

**这个判断是对的**，是这段代码里写得最好的部分。缓冲区满时丢最新帧、保住已有数据，
也是合理的取舍（`can_rx_drop` 计数器留着排查）。

### 8.5 优先级安排的意图

CMSIS-RTOS2 的数值**越大越高**（`osPriorityLow=8` → `osPriorityRealtime3=51`），
所以实际顺序是：

```
CAN_Rx_task   Realtime3 = 51   最高  ← 接收不能丢，先捞进来
UART_task     Realtime1 = 49   次高  ← 串口独占，且是阻塞轮询，得给足优先级
CAN_Tx_task   High7     = 47   第三  ← 状态回传
defaultTask   Normal    = 24   空转（CubeMX 模板留下的壳）
led_running   Low       =  8   最低
```

⚠️ 注意 `Realtime1`(49) **高于** `High7`(47)——名字看着像 "High7 更高"，实际不是。
这个次序导致串口空转时 CAN 发送被压住（见 §8.3 和 §7 ★ 条）。

真要改的话，把 `CAN_Tx_task` 提到 `osPriorityRealtime2`(50) 就能让它只低于 CAN 接收、
高于串口任务；或者更彻底——**把 USART2 改成 DMA + 中断**，
让 `UART_task` 真正阻塞在信号量上而不是空转 CPU。

`defaultTask` 是个空壳（只有 `osDelay(1)`），可以删掉省 512 字节栈（够跑一个舵机的固件）。

### 8.6 分层原则小结

| 层 | 该做什么 | 不该做什么 |
|---|---|---|
| ROS 2 (PC) | 运动学、规划、可视化、用户界面 | 硬实时控制 |
| KickPi | 协议转换、CAN 收发、网络 | 运动学计算 |
| STM32 | 实时收发、舵机串口、缓冲 | 规划、坐标变换 |
| 舵机 | 位置闭环 | 一切其他 |

**判断代码该放哪一层的标准：看它对延迟有多敏感。** 延迟敏感的往下放，算力密集的往上放。

### 第 4 步怎么做：把 CanServer 写成一个能用的程序

分两小步，**先让它能独立跑起来，再谈和 ROS 2 对接**。

**4a. 先把接口暴露出来**

现在 `Cansocket_object` 类整个定义在 `src/can_init.cpp` 里，
`include/can_init.h` 只有三个宏，`main.cpp` 拿不到这个类。
两种改法：

| 改法 | 说明 |
|---|---|
| 类搬进头文件 | 声明进 `can_init.h`，定义留在 `.cpp`；最贴近现在的写法 |
| 包一层 C 接口 | 导出 `can_open()` / `can_send()` / `can_recv()` 几个自由函数；更好被别的语言调 |

**顺带把 §7 里几条一起处理掉**（反正要动这个文件了）：`Can_Write` 不检查返回值、
按 `dlc` 而不是固定 8 字节读、`ioctl` 失败没判断、`Can_Socket_Init` 是 `void` 报不了错。

**4b. 写 main：一个最小的 CAN 收发循环**

第一个版本**不要碰网络**，就用命令行参数跑通：

```
CanServer send <id> <ask> <pos> <time>     # 发一条指令
CanServer monitor                          # 一直收 0x200 并打印
```

能用 `CanServer send 3 1 2000 500` 让舵机动起来、`CanServer monitor` 看到回包，
**第 4 步就算完成了**。这时候你已经把 §3.2 那份协议用代码实现了一遍。

**注意**：`can0` 得先起来，程序里可以用 `can_init.h` 那几个宏 + `system()`，
但**更稳的是让程序自己用 `ioctl(SIOCSCANBITTIMING)`**，或者干脆要求用户先手工 `ip link` 起好。
`system("ifconfig ...")` 那套在 Ubuntu 24.04 上 `ifconfig` 可能已经没装了（建议换 `ip`）。

### 第 5 步的岔路口：CanServer 要不要直接做 ROS 2 节点？

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 板子上装 ROS 2，CanServer 变 rclcpp 节点** | 一套东西，DDS 自动组网，不用自己定网络协议 | 板子现在**没装 ROS 2**；内存只有 3.8G；arm64 上编译 rclcpp 慢 |
| **B. CanServer 是普通 TCP/UDP 服务，ROS 2 侧写客户端** | 板子保持轻量，协议自己定，改起来快 | 要自己设计并维护一套网络协议 |

**建议先走 B**——现在最需要的是「快」，而且你的协议简单到只有 6 个字节。
等真的需要在板子上跑导航/规划了，再迁到 A 不迟。
